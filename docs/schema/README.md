# Schema pubblici

- `job-content.v1.json`: schema JSON (draft 2020-12) del contenuto di un annuncio di lavoro, versione 1 (PRODUCT.md §4.4).
  Descrive solo la forma dei dati; è lo stesso schema Zod usato da API, feed, import ed export.
- `candidate-export.v1.json`: schema JSON del file `candidate.json` dell'export di un candidato e dell'export dell'organizzazione (PRODUCT.md §6): anagrafica, candidature con consensi, messaggi, estrazione dal CV e note. Le date sono stringhe ISO 8601; i CV originali sono nello ZIP accanto al file e vi si fa riferimento con `applications[].cv.path`. Si rigenera con lo stesso comando.
- `migration-package.v1.json`: schema JSON del file `migration.json` del pacchetto di migrazione da un altro ATS (ADR 0009, PRODUCT.md §6). Il pacchetto è uno ZIP con `migration.json` alla radice e i file sotto `files/`; lo producono i connettori integrati, la skill per agenti o una persona a mano, e passa sempre dalla stessa validazione. Contiene `source` (sistema di origine, data dell'export, chi ha prodotto il pacchetto), `users` (solo per firmare le note, non crea account), `jobs` con le loro fasi (`stages[]`, `type` facoltativo tra i tipi di fase della tassonomia) e un `content` parziale dell'annuncio, `candidates` con l'eventuale `consent` (`givenAt`, `expiresAt`, `scopes`), `applications` con fase attuale, esito, date, risposte, file e storico delle fasi, `notes` e `messages` (email passate, mai inviate). Ogni elemento ha un `ref` stabile scelto da chi produce il pacchetto; le date sono ISO 8601 con fuso orario. Si rigenera con lo stesso comando.
  - Tutti gli oggetti sono chiusi (`additionalProperties: false`): un campo sconosciuto fa rifiutare il pacchetto, non viene ignorato. Così un punteggio non può entrare sotto un altro nome.
  - Mancano di proposito, e non vanno aggiunti: punteggi, voti, valutazioni delle schede di colloquio, valutazioni automatiche o "match", dati demografici o di categorie particolari (art. 9 GDPR), foto, data di nascita, genere. Il prodotto non decide e non dà voti alle persone (PRODUCT.md §2.4, ADR 0005) e raccoglie solo i dati che servono alla selezione (§6); i connettori scartano questi valori. Le note libere dei colloqui arrivano come note.
  - Mancano anche gli account e le credenziali: gli autori delle note diventano membri solo se l'email coincide con quella di un membro, altrimenti restano un nome. La fase `received` e gli id delle fasi li assegna il prodotto al momento della conferma.
  - Il file non descrive i controlli incrociati, che il prodotto applica sopra la forma (`parseMigrationPackage` di `@candydati/domain`): `ref` unici per raccolta (le fasi per annuncio), candidature che puntano a candidato, annuncio e fase di quell'annuncio esistenti, note e messaggi che puntano a record esistenti, percorsi dei file sotto `files/` senza `..`, un solo CV per candidatura, date di chiusura successive alla creazione, esito presente se e solo se c'è una data di chiusura. Anche i limiti di quantità (`MIGRATION_LIMITS`: 50.000 candidati, 100.000 candidature, 200.000 note, 200.000 messaggi, 120.000 file, 20 GiB in tutto) sono applicati dal prodotto.
- Le regole di pubblicazione del §5.1 (ruolo, RAL, modalità di lavoro, fasi, responsabilità, requisiti) non sono nel file:
  le applica `checkPublishable` di `@candydati/domain` sopra la forma.
- Per rigenerarlo dopo una modifica allo schema: `pnpm --filter @candydati/domain schema` (compila e scrive questo file).
- Una modifica incompatibile richiede una nuova versione (`job-content.v2.json`), senza riscrivere la v1.
- Le fasi del processo (`process[]`) hanno due campi opzionali, aggiunti senza cambiare versione perché compatibili con i dati esistenti:
  `id` (stringa stabile, `^[a-z0-9-]{1,40}$`; il server la assegna alle fasi che ne sono prive e la restituisce sempre) e `title`
  (titolo libero di 1-80 caratteri; se manca si mostra il tipo). I candidati sono legati all'`id`, non alla posizione.
- Fase 9, campi opzionali aggiunti senza cambiare versione (gli annunci esistenti restano validi): `employment` (`ccnl` con id da un elenco dei CCNL più diffusi, `ccnlOther`, `level`,
  `monthlyPayments` 12-16, `mealVoucher { amountPerDay, type: electronic | paper }`, `welfareAnnual`, `bonus`, `extraBenefits` con id da un elenco e `otherBenefits` libero) e
  `protectedCategories` (`none | reserved | also`, L. 68/99). Anche la conformità (annuncio rivolto a entrambi i sessi, requisiti discriminatori, categorie protette) non è nel file:
  la applica `checkCompliance` di `@candydati/domain`, e le violazioni chiare bloccano la pubblicazione tramite `checkPublishable`.
